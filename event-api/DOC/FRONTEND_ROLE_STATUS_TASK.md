# Задача: Реализация проверки статуса запроса на повышение роли (Frontend)

## Общее описание

Необходимо реализовать интерфейс для пользователей, у которых нет прав на создание контента (например, роль `creator`). Пользователь должен иметь возможность запросить повышение роли, отслеживать статус своей заявки и видеть причину отказа, если заявка была отклонена.

## Пользовательский сценарий (User Flow)

1.  **Попытка доступа к защищенному разделу:**
    - Пользователь переходит на страницу создания карточек (или другой защищенный раздел).
    - Система проверяет текущую роль пользователя.
    - Если прав недостаточно, отображается экран-заглушка (Placeholder) или модальное окно.

2.  **Состояния экрана запроса прав:**
    - **Состояние 1: Заявка отсутствует (Initial State)**
      - Пользователь видит сообщение: "У вас нет прав на создание контента".
      - Кнопка/Форма: "Запросить права автора".
      - Поле ввода: "Причина запроса" (обязательное, мин. 10 символов).
      - Действие: Отправка POST-запроса.

    - **Состояние 2: Заявка на рассмотрении (Pending)**
      - Если пользователь уже отправил заявку, и она находится в статусе `pending`.
      - Отображается статус: "Ваша заявка находится на рассмотрении".
      - Информационное сообщение: "Верификация может занять некоторое время. Пожалуйста, зайдите позже."
      - Кнопка повторной отправки заблокирована или скрыта.

    - **Состояние 3: Заявка одобрена (Approved)**
      - Если заявка перешла в статус `approved`.
      - Пользователь автоматически получает доступ к функционалу (редирект на создание карточки или разблокировка интерфейса).
      - Можно показать одноразовое уведомление: "Поздравляем! Вам выданы права автора."

    - **Состояние 4: Заявка отклонена (Rejected)**
      - Если заявка перешла в статус `rejected`.
      - Отображается статус: "Ваша заявка была отклонена".
      - **Важно:** Отобразить причину отказа (`rejection_reason`), полученную от API.
      - Пользователь имеет возможность исправить данные и отправить заявку повторно (возврат к Состоянию 1 с предзаполненными или пустыми полями).

## Технические требования

### API Эндпоинты

1.  **Получение списка заявок пользователя:**
    - `GET /api/users/request-role/all`
    - Использовать для проверки текущего статуса при загрузке страницы.
    - Ответ (пример):
      ```json
      [
        {
          "id": "uuid",
          "role": "creator",
          "status": "pending", // или "rejected", "approved"
          "reason": "Хочу создавать ивенты",
          "rejection_reason": "",
          "created_at": "..."
        }
      ]
      ```

2.  **Отправка новой заявки:**
    - `POST /api/users/request-role`
    - Тело запроса:
      ```json
      {
        "role": "creator",
        "reason": "Описание причины..."
      }
      ```

### Логика Frontend

- При загрузке защищенного компонента делать запрос `GET /api/users/request-role/all`.
- Фильтровать заявки по интересующей роли (например, `creator`).
- Брать самую последнюю актуальную заявку.
- В зависимости от `status` рендерить соответствующий UI.

### UI Компоненты (Рекомендации)

- **StatusBadge:** Компонент для отображения текущего статуса (Желтый для Pending, Красный для Rejected, Зеленый для Approved).
- **RejectionMessage:** Блок с текстом ошибки от администратора.
- **RequestForm:** Форма с валидацией длины сообщения.

## Критерии приемки (Acceptance Criteria)

1.  Пользователь без прав не может попасть в создание карточек.
2.  Пользователь видит статус "На рассмотрении" после отправки.
3.  Пользователь видит причину отказа, если админ отклонил заявку.
4.  Пользователь может отправить повторную заявку после отказа.
5.  При одобрении интерфейс разблокируется.
