# Discovery-модуль: Руководство по работе

[← Вернуться к документации](./INDEX.md) | [Техническая документация движка](../Reference/DISCOVERY_ENGINE.md)

## Обзор

Discovery-модуль — это система персонализированного подбора мероприятий для пользователей. Модуль работает по принципу «карточек»: пользователь последовательно просматривает предложенные события и реагирует на каждое из них.

### Ключевые особенности

- **Последовательный просмотр** — пользователь видит одно событие за раз и должен отреагировать на него, прежде чем увидеть следующее
- **Управление конфликтами** — при бронировании события все пересекающиеся по времени мероприятия автоматически откладываются
- **Персонализированная очередь** — каждый пользователь имеет свою очередь событий с учётом его предыдущих действий
- **Фильтрация** — возможность фильтровать события по типу, цене, месту и датам

---

## Как это работает для пользователя

### Шаг 1: Получение следующего события

Пользователь запрашивает следующее событие (`/v1/api/next`) для просмотра. Система возвращает:

- Информацию о событии (название, описание, время, место)
- Флаг конфликта, если событие пересекается с уже забронированным
- Количество оставшихся событий в очереди

### Шаг 2: Реакция на событие

Пользователь может выполнить одно из следующих действий:

| Действие         | Описание                           | Результат                                                    |
| ---------------- | ---------------------------------- | ------------------------------------------------------------ |
| **Like** (👍)    | Отметить событие как понравившееся | Событие перемещается в конец очереди, записывается в историю |
| **Dislike** (👎) | Отметить событие как неинтересное  | Событие безвозвратно удаляется из очереди                    |
| **Neutral** (⏭️) | Пропустить событие                 | Событие перемещается в конец очереди                         |
| **Book** (📅)    | Забронировать событие              | Событие бронируется, конфликтующие события откладываются     |

### Шаг 3: Бронирование

При бронировании события:

1. Событие фиксируется как забронированное
2. Все события, пересекающиеся по времени, помечаются как «конфликтные»
3. Конфликтные события перемещаются в конец очереди
4. Пользователь получает список ID конфликтующих событий

## Структура очереди

Очередь событий разделена на две части:

```text
┌─────────────────────────────────────────────────────┐
│                  ОСНОВНАЯ ОЧЕРЕДЬ                   │
│  События без конфликтов, доступные для просмотра   │
├─────────────────────────────────────────────────────┤
│                 ОЧЕРЕДЬ КОНФЛИКТОВ                  │
│  События, пересекающиеся с забронированными        │
└─────────────────────────────────────────────────────┘
```

**Правила работы очереди:**

- Сначала показываются события из основной очереди
- Когда основная очередь пуста, начинают показываться конфликтные события
- Конфликтные события помечаются соответствующим флагом

## Фильтрация событий

При запросе следующего события можно применить фильтры:

| Фильтр         | Описание                                 | Пример                         |
| -------------- | ---------------------------------------- | ------------------------------ |
| **types**      | Типы событий                             | `["концерт", "выставка"]`      |
| **priceTypes** | Ценовая категория                        | `["free", "paid", "donation"]` |
| **places**     | Название площадки (частичное совпадение) | `["Парк Горького"]`            |
| **dateFrom**   | Начало временного диапазона              | `2025-01-15T00:00:00Z`         |
| **dateTo**     | Конец временного диапазона               | `2025-01-20T23:59:59Z`         |

При применении фильтров очередь перестраивается с учётом указанных критериев.

## Обработка конфликтов

### Что такое конфликт?

Конфликт возникает, когда два события пересекаются по времени. Если пользователь бронирует одно из них, второе автоматически помечается как конфликтное.

### Пример

1. Пользователь видит «Концерт A» (18:00–21:00)
2. Пользователь бронирует «Концерт A»
3. «Выставка B» (19:00–22:00) пересекается по времени
4. «Выставка B» перемещается в очередь конфликтов
5. При показе «Выставки B» пользователь видит предупреждение о конфликте

### Информация о конфликте

При получении конфликтного события система возвращает:

- ID события, с которым произошёл конфликт
- Причину конфликта
- Время, когда конфликт был зафиксирован

---

## История действий

Все действия пользователя сохраняются в истории:

- **Что хранится:** ID пользователя, ID события, тип действия, временная метка
- **Зачем:** Для аналитики, исключения просмотренных событий, восстановления состояния
- **Идемпотентность:** Повторные одинаковые действия не создают дубликатов

---

## Управление каталогом событий

### Обновление событий

Каталог событий можно обновить двумя способами:

1. **Замена событий** — полная замена каталога новым набором
2. **Обновление каталога** — замена событий + сброс всех пользовательских очередей

### Автоматические обновления

Модуль поддерживает уведомления через Redis Pub/Sub:

- При одобрении нового события публикуется сообщение
- Подписчики обновляют свои каталоги

## Возможные ошибки

| Ошибка                        | Описание                                 | Что делать                                 |
| ----------------------------- | ---------------------------------------- | ------------------------------------------ |
| **Очередь пуста**             | Все события просмотрены                  | Ожидать появления новых событий            |
| **Неверный порядок действия** | Попытка действия над устаревшим событием | Запросить актуальное событие через /next   |
| **Событие не найдено**        | Событие было удалено из каталога         | Обновить интерфейс и запросить /next       |
| **Недопустимое действие**     | Передан неизвестный тип действия         | Использовать: like, dislike, neutral, book |

## FAQ

### Как сбросить очередь пользователя?

Очередь сбрасывается автоматически при обновлении каталога событий. Также доступен ручной сброс через административный API.

### Что происходит с конфликтными событиями после окончания забронированного?

Конфликтные события остаются в очереди конфликтов. Они будут показаны пользователю после всех событий из основной очереди.

### Можно ли вернуть пропущенное событие?

События с действием «Neutral» автоматически перемещаются в конец очереди и будут показаны снова. События с «Like» или «Dislike» повторно не показываются.

### Как работает фильтрация с сохранённой очередью?

При применении фильтров очередь перестраивается заново с учётом фильтров. Оригинальная очередь не изменяется.
